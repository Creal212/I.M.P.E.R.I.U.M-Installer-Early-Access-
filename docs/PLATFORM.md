# How I.M.P.E.R.I.U.M works

I.M.P.E.R.I.U.M combines AI-assisted work with separate working copies, inspectable changes and a deliberate route back to your original project.

## Main, Clone and saved states

**Main** is your original selected project folder. A **Clone** is a separate working copy admitted through import inspection and your exclusions. Main's saved location supports patching; it is not a continuous network connection. If Main moves, review and reconnect the folder in project details.

Saved States record clone content associated with import and patches. They are not a full backup of your computer. Restoring a clone state does not automatically restore Main. A missing Main can block apply/revert without making every clone-only activity unavailable.

The local engine manages task boundaries and patch decisions. Instructions in project files, prompts, websites or skills do not grant permission to access unrelated local files or directly modify Main. These controls are not a claim that every possible exploit has been eliminated.

## Workspace

Workspace is the project engineering area: admitted files, editing, supported previews, scoped tasks, changed-file review, activity and saved reports. Direct, routed and collaborative build styles still depend on actual model/tool capability and the selected environment.

Host-accepted file changes and recorded tool results establish what happened. A model's statement that it edited or tested something is not evidence. Even valid execution evidence does not guarantee the code is correct.

## Studio and Blueprint

Studio is a conversation environment for supplied text and attachments. Compatible connections can create supported session deliverables. It is not automatic live collaboration on Main. A generated file must exist and meet the relevant checks before it becomes an available download.

Blueprint is a separate planning conversation: capture the outcome, requirements and risks, review steps, and hand approved work to Workspace. Planning is not implementation. Its history remains separate from Studio.

## Patches and rollback

Kept clone changes can become a named patch. Review actual files, prerequisites and evidence before Apply to Main. Pending, rejected, failed and applied records have different meanings.

Rejecting pending work is not reverting an applied change. Rollback uses saved restoration evidence and a preview; newer overlapping edits can require review. Keep independent backups.

## Inspection and previews

Project checks look for supported sensitive and suspicious-content patterns. Findings can lead to review, ignore, quarantine or deletion as authorized. Quarantine retains a copy; it is not deletion. Missing coverage is different from a confirmed issue.

Project status must be interpreted for its project, scope and time. Refreshing evidence does not erase genuine findings. A pass does not certify absence of secrets, malware or vulnerabilities.

**Shadow Verify is Experimental.** Supported previews may use disclosed temporary substitutes for missing dependencies or services. Those substitutes do not prove the real integration works. Review unresolved requirements and confirmations involving edited code.

## Providers, skills and permissions

Available local models, APIs and supported account connections can provide different capabilities. Sign-in, task execution and media entitlement are separate. Offline tasks need local components installed; cloud tasks can send permitted task content to the provider. See [Privacy](PRIVACY.md).

Skills are reusable instructions, not extra permissions. Supported Hermes-style install input resolves a source instead of executing arbitrary pasted shell commands. Review source, tool compatibility and third-party terms. Learned procedures remain subject to successful evidence and environment controls.
